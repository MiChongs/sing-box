`algorithm` 决定 Smart 从已排好序的候选列表中先拨哪一个。所有算法都只做一件事：**把一个候选换到首位**，不会增删候选，也不会改变权重本身。候选列表如何产生见 [工作原理](../how-it-works/#分层取候选)。

## 一览

| 算法 | 别名 | 类型 | 首位的选法 |
|---|---|---|---|
| `strict-best`（默认） | `auto`、`best`、`strict` | 排序型 | 不调整，直接用排名第一的 |
| `weighted-random` | `random`、`weighted` | 选择型 | 前 5 名中按名次加权随机 |
| `least-loaded` | `least-load`、`load` | 排序型 | 前 3 名中活跃 TCP 连接最少的 |
| `fastest-recent` | `fastest`、`recent` | 排序型 | 前 5 名中近期 RTT 最低的 |
| `sticky-session` | `sticky`、`session` | 选择型 | 该目标上次成功使用的节点 |
| `round-robin` | `rr` | 选择型 | 按组内计数器轮流 |
| `weighted-rr` | `wrr`、`weighted-round-robin` | 选择型 | 前 5 名按 5:4:3:2:1 的次数轮流 |
| `p2c` | `power-of-two`、`two-choices` | 选择型 | 前 5 名中随机取 2 个，选更快的 |
| `latency-banded` | `banded`、`latency-bands` | 排序型 | 前 5 名按延迟分档，在最低档内随机 |
| `consistent-hashing` | `consistent-hash`、`chash`、`ch`、`consistent`、`jump-hash` | 选择型 | 按目标哈希到固定位置 |

取值不区分大小写，下划线与空格等同于连字符，例如 `Least_Loaded` 也有效。无法识别的值不会报错，而是回退到 `strict-best` 并记录一条 WARN，列出所有合法取值。启动日志中的 `algorithm=` 是实际生效的算法。

### 排序型与选择型

两类算法的区别不只在首位的选法：

- **第 0 轮拨号宽度**：排序型同时拨前 2 个候选（首选节点近期成功率 ≥ 95% 时只拨 1 个），选择型只拨 1 个。
- **请求场景重排**：只对排序型生效。下载、流媒体按峰值下载速度，交互、实时、语音按近期 RTT 重排前 5 个。

所以选择型算法的选择更“确定”，排序型算法在首选节点慢的时候更快地切到第二个。

## 各算法详解

### strict-best

不做任何调整，按权重排名拨号。适合大多数场景，也是默认值。配合 `hysteresis` 可以减少相近节点之间的来回切换。

### weighted-random

在前 5 名中随机选一个，概率按**名次**而非权重分配：第 1 名 5/15，第 2 名 4/15，依次到第 5 名 1/15。适合想把流量分散到几个好节点、又不想太平均的场景。

### least-loaded

在前 3 名中选当前活跃 TCP 连接最少的节点，连接数相同时保留排名靠前的。UDP 连接不计入负载。适合下载、大量并发连接的场景。

### fastest-recent

在前 5 名中选近期 RTT 最低的节点。近期 RTT 是最近约 30 个样本的首字节延迟滑动平均，缓存 250 ms；没有数据的节点不参与比较。适合对延迟敏感、而节点质量变化较快的场景。

### sticky-session

同一目标优先使用上一次成功的节点（TCP 与 UDP 分开记录）。只要该节点仍可用、没有被判为可疑、也没有手动指定，Smart 会走快速路径直接拨它，跳过整个候选流程。记录超过 8192 条时整体清空。

适合登录态与 IP 绑定的网站，例如 AI 服务、银行、部分流媒体。

### round-robin

每次拨号把组内计数器加 1，对候选数量取模选出首位。计数器由整个组共享，不区分目标。适合需要平均分摊流量的场景。

### weighted-rr

按名次加权的轮询：在前 K 个候选（K 最多为 5）中，第 1 名连续出现 5 次，第 2 名 4 次，依此类推。比 `round-robin` 更偏向好节点，又比 `strict-best` 分散。

### p2c

“二选一”：从前 5 名中随机取两个不同的节点，近期 RTT 都已知且不同则选更低的；否则选活跃连接更少的；仍相同则取先抽到的那个。在负载与延迟之间取得平衡，适合作为通用默认。

### latency-banded

把前 5 名按近期 RTT 分成三档：低于 50 ms、低于 150 ms、150 ms 及以上或未知，在最低的非空档内均匀随机。避免总是挤在同一个最快节点上，又不会用到明显更慢的节点。适合交互类流量。

### consistent-hashing

以 `t|目标` 或 `u|目标` 为键做 xxhash，再用 jump hash 映射到候选列表的一个位置。同一目标在候选列表不变时总是落到同一个节点，适合需要固定出口 IP 的目标。

<Callout type="note" title="一致性的前提">
  映射基于候选列表的长度与顺序。节点失效、权重变化导致候选列表改变时，目标可能被映射到其他节点。需要更强的粘性时，用 `sticky-session`。
</Callout>

## 运行时切换

通过 Clash API 可以在不重启的情况下切换算法：

```bash
curl -X PUT http://127.0.0.1:9090/smart/groups/auto/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"algorithm":"p2c"}'
```

```json
{ "group": "auto", "requested": "p2c", "applied": "p2c", "previous": "strict-best" }
```

请求体必须是 JSON 对象。`applied` 是实际生效的算法：传入无法识别的值时，它会是 `strict-best`。切换只在本次运行中有效，重启后恢复配置文件中的值。

## 与其他机制的关系

- **`policy_priority`** 在算法之前生效：系数大于 1 的节点先被排到前面，算法再从前几名中挑选。
- **`hysteresis`** 在算法之后生效：窗口内该目标上一次使用的节点只要仍在候选中，就会被换回首位，覆盖算法的选择。与 `sticky-session` 不同，它不走快速路径，仍会经过完整的过滤流程。
- **手动指定**时候选列表只有被指定的节点，算法不起作用。

## 如何选择

| 场景 | 建议 |
|---|---|
| 通用，不确定选什么 | `strict-best`，或 `p2c` |
| 登录态与出口 IP 绑定 | `sticky-session` |
| 同一网站需要固定出口，但可以接受偶尔变化 | `consistent-hashing` |
| SSH、远程桌面、网页交互 | `latency-banded` 或 `fastest-recent`，加 `hysteresis` |
| 下载、更新、大量并发 | `least-loaded` |
| 平摊流量、避免单节点过载 | `weighted-rr` 或 `round-robin` |

不同类型的流量可以通过路由规则分到使用不同算法的 Smart 组，见 [示例配置](../examples/#按流量类型分组)。
