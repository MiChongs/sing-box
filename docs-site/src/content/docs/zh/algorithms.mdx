`algorithm` 决定 Smart 组在已经排好序的候选节点中**先拨哪一个**。大多数用户保持默认的 `strict-best` 即可；当你希望流量分散到几个节点、同一网站固定出口，或对延迟特别敏感时，再来这里换一个算法。

本页只适用于 `smart` 组。`smart-loadbalance` 组没有 `algorithm`，它用 `balance.strategy` 在整个地区内分配连接，见 [Smart 负载均衡](../smart-loadbalance/)。

## 算法管什么，不管什么

每条连接到来时，Smart 先按学到的权重为这个目标排出一个候选列表（最多 10 个节点，过程见 [工作原理](../how-it-works/#分层取候选)），然后才轮到算法。算法只做一件事：**把列表中的某一个节点换到第一位**。它不会增删候选，也不会改变任何权重。

举个例子：某个网站的候选列表是 `[HK-01, HK-02, JP-01, SG-01, US-01]`。

- `strict-best` 什么都不动，先拨 `HK-01`；
- `round-robin` 这次可能把 `JP-01` 换到第一位，下次换成别的；
- `sticky-session` 如果上次用的是 `HK-02`，就把 `HK-02` 换到第一位。

被换到第一位的节点拨号失败时，Smart 照常按列表继续尝试其他候选，所以选哪个算法都不会降低可用性，只影响“首选谁”。

## 一览

| 算法 | 别名 | 类型 | 首选的选法 |
|---|---|---|---|
| `strict-best`（默认） | `auto`、`best`、`strict` | 排序型 | 不调整，直接用排名第一的 |
| `weighted-random` | `random`、`weighted` | 选择型 | 前 5 名中按名次加权随机 |
| `least-loaded` | `least-load`、`load` | 排序型 | 前 3 名中活跃 TCP 连接最少的 |
| `fastest-recent` | `fastest`、`recent` | 排序型 | 前 5 名中近期首字节延迟最低的 |
| `sticky-session` | `sticky`、`session` | 选择型 | 该目标上次成功使用的节点 |
| `round-robin` | `rr` | 选择型 | 按组内计数器轮流 |
| `weighted-rr` | `wrr`、`weighted-round-robin` | 选择型 | 前 5 名按 5:4:3:2:1 的次数轮流 |
| `p2c` | `power-of-two`、`two-choices` | 选择型 | 前 5 名中随机取 2 个，选更快的 |
| `latency-banded` | `banded`、`latency-bands` | 排序型 | 前 5 名按延迟分档，在最快的一档内随机 |
| `consistent-hashing` | `consistent-hash`、`chash`、`ch`、`consistent`、`jump-hash` | 选择型 | 按目标哈希到固定位置 |

写法很宽松：不区分大小写，下划线、空格与连字符等同，例如 `Least_Loaded` 也有效。写错的值**不会让配置报错**，而是回退到 `strict-best`，并记录一条 WARN，列出所有合法取值。以启动日志为准：

```
smart[auto] started: 42 outbounds, ... algorithm=p2c hysteresis=off ml=off collect=off
smart[auto] algorithm: p2c (confirmed in PostStart)
```

非默认算法会额外打印第二行，便于用 `grep` 确认。

### 排序型与选择型

两类算法的区别在于“选完之后还竞不竞速”：

- **排序型**只把更合适的节点往前挪，前几名仍被视为差不多好。第 0 轮会**同时拨前 2 个**候选，谁先连上用谁；首选节点近期成功率达到 95% 时只拨 1 个，省掉一次多余的连接。下载、流媒体类请求还会按峰值下载速度，SSH、远程桌面、游戏、语音类请求按近期延迟，重新排列前 5 个候选。
- **选择型**已经为这条连接挑定了一个节点，第 0 轮**只拨这一个**，不与第二名竞速，否则轮询、粘性等效果会被打乱。为了不因此变慢，被选中的节点有可疑迹象（近期拨号失败、被判定不可用，或还没有过成功的拨号或探测）时，250 ms 后会再拨排名下一位的节点作为对冲，先连上的胜出。

所以，选择型算法的结果更“确定”，排序型算法在首选节点变慢时切换得更快。

## 各算法详解

### strict-best

不做任何调整，按权重排名拨号。适合大多数场景，也是默认值。如果发现相近的几个节点之间来回切换，可以加上 `hysteresis`。

### weighted-random

在前 5 名中随机选一个，概率按**名次**而不是权重分配：第 1 名 5/15，第 2 名 4/15，依次到第 5 名 1/15。适合想把流量分散到几个好节点、又不想平均分配的场景。

### least-loaded

在前 3 名中选当前活跃 TCP 连接最少的节点，连接数相同时保留排名靠前的。只统计经本组建立的 TCP 连接，UDP 不计入。适合下载、大量并发连接的场景。

### fastest-recent

在前 5 名中选“近期首字节延迟”最低的节点。近期延迟是该节点最近约 30 个样本的首字节延迟滑动平均，节点至少累积 11 个样本后才有值，读数缓存 250 ms；还没有数据的节点不参与比较，全部没有数据时保持原顺序。适合对延迟敏感、而节点质量变化较快的场景。

### sticky-session

同一目标优先使用上一次成功的节点（TCP 与 UDP 分开记录）。只要该节点仍可用、没有被判为可疑，并且没有手动指定节点，Smart 会走快速路径直接拨它，跳过整个候选流程，连接建立最快。

记录没有过期时间：节点不可用时自然换到别的节点，成功后记录随之更新；记录超过 8192 条时整体清空（每 5 分钟检查一次）。

适合登录态与出口 IP 绑定的网站，例如 AI 服务、银行、部分流媒体。

### round-robin

每次拨号把组内计数器加 1，再对本次候选数量取模，选出首选。计数器由整个组共享、不区分目标，候选列表又因目标而异，所以它是“大致轮流”，不是严格按节点名排队。适合希望平摊流量的场景。

### weighted-rr

按名次加权的轮询：在前 K 个候选（K 最多为 5）中，第 1 名连续做 5 次首选，第 2 名 4 次，依此类推，再从头开始。比 `round-robin` 更偏向好节点，又比 `strict-best` 分散。

### p2c

“二选一”：从前 5 名中随机取两个不同的节点。两者的近期首字节延迟都已知且不同，就选更低的；否则选活跃连接更少的；仍相同则取先抽到的那个。在负载与延迟之间取得平衡，适合作为通用默认。

### latency-banded

把前 5 名按近期首字节延迟分成三档：低于 50 ms、50–150 ms、150 ms 及以上（还没有延迟数据的节点也归入这一档），在最快的非空档内均匀随机。既不会总挤在同一个最快节点上，也不会用到明显更慢的节点。适合网页浏览等交互类流量。

### consistent-hashing

以 `t|目标` 或 `u|目标` 为键做哈希（xxhash），再用 jump hash 映射到候选列表的一个位置。同一目标在候选列表不变时总是落到同一个节点，不同目标则均匀分散到各个候选上。没有目标（直连 IP 且未嗅探到域名）时不调整。适合需要固定出口 IP 的目标。

<Callout type="note" title="一致性的前提">
  映射基于候选列表的长度与顺序。节点失效、权重变化导致候选列表改变时，目标可能被映射到其他节点。需要更强的粘性时，用 `sticky-session`。
</Callout>

## 运行时切换

通过 Clash API 可以在不重启的情况下切换算法：

```bash
curl -X PUT http://127.0.0.1:9090/smart/groups/auto/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"algorithm":"p2c"}'
```

```json
{ "group": "auto", "requested": "p2c", "applied": "p2c", "previous": "strict-best" }
```

- 请求体必须是 JSON 对象。`applied` 是实际生效的算法：传入无法识别的值时，它会是 `strict-best`。
- 切换立即作用于之后的新连接，已建立的连接不受影响。
- 切换只在本次运行中有效，不写回配置，重启后恢复配置文件中的值。
- 对 `smart-loadbalance` 组调用会返回 400，请改用 `PUT /smart/groups/{name}/balance`。

当前生效的算法可以在 `GET /proxies/{name}` 或 `GET /smart/groups` 的 `algorithm` 字段中查看。

## 与其他机制的关系

一条连接的候选列表依次经过下面几步，后一步可以覆盖前一步：

1. **`policy_priority`** 先按节点名称系数重排，系数大于 1 的节点排到前面，见 [节点偏好与手动指定](../priority-and-pinning/)。
2. **选路算法**从调整后的前几名中选出首选。
3. **`hysteresis`** 最后生效：窗口内这个目标上一次成功使用的节点只要仍在候选中，就换回第一位，覆盖算法的选择。与 `sticky-session` 不同，它不走快速路径，仍会经过完整的过滤流程。

此外，**手动指定**节点后候选列表只有被指定的节点，算法不起作用；只有当被指定的节点拨号失败或熔断时，Smart 才临时按算法选择其他节点。

## 如何选择

| 场景 | 建议 |
|---|---|
| 通用，不确定选什么 | `strict-best`，或 `p2c` |
| 登录态与出口 IP 绑定 | `sticky-session` |
| 同一网站需要固定出口，但可以接受偶尔变化 | `consistent-hashing` |
| SSH、远程桌面、网页交互 | `latency-banded` 或 `fastest-recent`，加 `hysteresis` |
| 下载、更新、大量并发 | `least-loaded` |
| 平摊流量、避免单节点过载 | `weighted-rr` 或 `round-robin` |

不同类型的流量可以通过路由规则分到使用不同算法的 Smart 组，见 [示例配置](../examples/#按流量类型分组)。

<Callout type="note" title="想把连接分摊到整个地区">
  这些算法只在前 3–5 名候选之间调整，`round-robin` 等也不区分地区。需要把连接分摊到某个地区的全部好节点、并让同一网站保持出口国家时，使用 [Smart 负载均衡](../smart-loadbalance/)（`smart-loadbalance` 组）。
</Callout>
