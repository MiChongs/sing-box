Smart 的学习结果先保存在内存里，每 5 分钟写入 sing-box 的缓存文件，重启后接着用。这一页说明存了什么、占多少、怎样清空。只想正常使用时记住一点：**开启 `experimental.cache_file`**，否则每次重启都从零学起。

## 数据保存在哪里

Smart 使用 `experimental.cache_file` 指定的 bbolt 数据库（默认数据目录下的 `cache.db`），所有数据放在其中的 `smart_score` bucket 里。旧版 Smart 使用的 `smart_stats` bucket 不再被识别，缓存文件打开时会被自动删除，旧数据不会迁移。命令行版本需要设置 `cache_file.enabled: true`；SFA / SFW / SFL 图形客户端始终启用缓存文件。

没有缓存文件时，Smart 照样学习、封锁与选择，只是这些数据只在内存中：重启后丢失，手动指定与 `smart-loadbalance` 的地区锁定也不会保留。

### 存了什么

| 键 | 内容 |
|---|---|
| `cell/<组>/<层>/<网络>/<地址族>/<节点>[/<服务键>]` | 全局、地址族与服务层的证据单元：衰减后的成功与失败、失败计数与退避期、连接质量、重传平均、累计流量与时长、建连与响应耗时的平均值 |
| `host/<组>/<tcp\|udp>/<键>` | 一个网站或服务键的封锁记录 |
| `gblock/<组>/<节点>` | 整组封锁（手动、`unstable`）及截止时间 |
| `rec/<组>/pin/` | 手动指定的节点 |
| `rec/<组>/exit/<节点>` | 成员的出口国家、IP 与 ASN |
| `rec/<组>/region/` | `smart-loadbalance` 的地区锁定，以及运行中切换过的模式、策略与亲和 |
| `rec/<组>/exitgeo/<节点>` | `smart-loadbalance` 出口探测得到的国家与出口 IP |

键中的 `/` 与 `%` 会被转义，名称含 `/` 的组和节点也能正确存取。

以下内容**只在内存中**，重启后重新积累：精确目标层（`host:port`）的证据、延迟与吞吐等新鲜性能数据（本来 2 分钟就过期）、各服务的在任节点、服务池、探索预算、健康检查状态、网站眼中的出口与出口嫌疑、响应探测的限流状态、排名缓存；`smart-loadbalance` 的目标地区记忆、会话亲和与地区探测结果。

### 写盘与恢复

- 证据单元、封锁记录与整组封锁每 5 分钟写一次，退出时再写一次；每次写入都整体替换这个组的旧数据。
- 手动指定、出口信息与 `smart-loadbalance` 的运行时状态在变化时立即写入。
- 启动时恢复仍是本组成员的节点的数据；衰减按记录中的时间戳继续计算，所以停机一夜后，旧的成功与失败自然变轻。尚未到期的整组封锁、手动指定（节点仍在组内时）也会恢复。

### 成员与组的变化

- 节点离开本组（例如订阅更新后被删除）时，它在本组的内存数据立即删除，下一次写盘时从缓存文件中消失。
- 从配置中删除的**整个组**，数据会一直留在缓存文件里，不会自动清理；需要时删除缓存文件即可。
- 组改名相当于删除旧组、新建一个组。

### 手动清空

| 接口 | 范围 | 返回 |
|---|---|---|
| `DELETE /proxies/{name}/weights` | 一个组 | 删除的条目数 `{"group", "deleted": {"aggregate", "site", "exact", "blocks"}}` |
| `POST` / `DELETE /cache/smart/flush/{name}` | 一个组（名称不是 Smart 组时清空全部） | 204 |
| `POST` / `DELETE /cache/smart/flush` | 当前配置中的全部 Smart 组 | 204 |

清空会删除这个组的全部证据、在任节点、服务池与探索预算、所有封锁记录（包括 `manual`）、整组封锁、手动指定、出口信息，以及缓存文件中的全部记录；健康状态重置，`smart-loadbalance` 的地区锁定与运行时设置恢复为配置值并重新识别地区。适合节点大换血之后，或怀疑数据被异常情况污染的时候。

## 内存

证据单元由所有 Smart 组共用的表保存，每张表分成 64 个分片，满了以后按“最久没用”近似淘汰：

| 表 | 容量 |
|---|---|
| 全局与地址族 | 4096 个单元 |
| 服务层 | 8192 个单元 |
| 精确目标 | 16384 个单元 |

在任节点最多 4096 条；封锁记录按网站保存，一周没有新失败即清理。诊断接口的 `cache` 显示三张表当前的大小与累计淘汰数；淘汰数持续快速增长，说明访问的服务远多于容量，较少使用的服务会更频繁地从零开始学习。

## 每条连接的开销

选择路径为节点很多的组做了优化：

- 服务池把每次评分限制在少数成员上，池外成员只在需要备用时排序；
- 读取证据不需要写锁，健康状态是无锁快照，连接计数是原子操作；只有建连、首次响应、每秒最多一次的进展记录、吞吐窗口与连接关闭时才更新评分；
- 连接质量、LightGBM 推理、封锁判定与响应探测都在连接关闭后的后台进行，不拖慢连接本身。

在 i7-14650HX 上的并行基准测试中，100 个成员的组：引擎选择约 2.3 µs、3 次内存分配；包括过滤、选择与排序的完整拨号计划约 6.4 µs、7 次分配。

## 手机与低内存设备

- 默认的 `interval: 5m` 与 `idle_timeout: 30m` 已经兼顾省电：不用时健康检查暂停，系统休眠时所有后台任务跳过；
- 不需要时不要开启 `use_lightgbm` 与 `collect_data`：它们会打开 ASN 与国家数据库，模型本身也占用一些内存；
- 不需要 ASN 归并时不要开启 `prefer_asn`，同样可以不打开 ASN 数据库。
