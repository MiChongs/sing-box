Smart keeps what it learns in memory, writes it to sing-box's cache file every 5 minutes, and picks up where it left off after a restart. This page covers what is stored, how much, and how to flush it. For normal use remember one thing: **enable `experimental.cache_file`**, otherwise every restart starts learning from scratch.

## Where data lives

Smart uses the bbolt database of `experimental.cache_file` (`cache.db` in the data directory by default) and keeps everything in its `smart_score` bucket. The `smart_stats` bucket of the old Smart is no longer recognized and is deleted automatically when the cache file opens; old data is not migrated. The command-line version needs `cache_file.enabled: true`; the SFA / SFW / SFL GUI clients always have a cache file.

Without a cache file, Smart still learns, blocks and chooses, but only in memory: everything is lost on restart, including the manual pin and the region lock of `smart-loadbalance`.

### What is stored

| Key | Content |
|---|---|
| `cell/<group>/<layer>/<network>/<family>/<node>[/<service key>]` | Evidence cells of the global, family and service layers: decayed successes and failures, failure streak and backoff, connection quality, retransmission average, total traffic and duration, average connect and response times |
| `host/<group>/<tcp\|udp>/<key>` | Block records of one site or service key |
| `gblock/<group>/<node>` | Group-wide blocks (manual, `unstable`) with their deadlines |
| `rec/<group>/pin/` | The pinned node |
| `rec/<group>/exit/<node>` | A member's exit country, IP and ASN |
| `rec/<group>/region/` | The region lock of `smart-loadbalance`, plus any mode, strategy or affinity switched at runtime |
| `rec/<group>/exitgeo/<node>` | Exit country and IP from `smart-loadbalance` exit detection |

`/` and `%` in key parts are escaped, so groups and nodes with `/` in their names work.

These live **in memory only** and rebuild after a restart: exact-target (`host:port`) evidence, fresh performance data such as latency and goodput (which expires after 2 minutes anyway), each service's incumbent, the serving pools, exploration budgets, health-check state, site-specific exits and exit suspicions, response-probe throttles, and the ranking cache; for `smart-loadbalance`, the per-target region memory, affinity bindings and region-probe results.

### Writing and restoring

- Evidence cells, block records and group-wide blocks are written every 5 minutes and once more on shutdown; each write replaces the group's previous data as a whole.
- The manual pin, exit info and the runtime state of `smart-loadbalance` are written as soon as they change.
- At startup, data of nodes that are still members is restored; decay continues from the stored timestamps, so after a night off the old successes and failures weigh less on their own. Unexpired group-wide blocks and the manual pin (if the node is still a member) are restored too.

### Members and groups that change

- When a node leaves the group (removed by a subscription update, say), its in-memory data for the group is dropped at once and disappears from the cache file at the next write.
- Data of a **whole group** removed from the config stays in the cache file and is not cleaned up; delete the cache file if you need to.
- Renaming a group is the same as removing the old group and adding a new one.

### Flushing

| Endpoint | Scope | Response |
|---|---|---|
| `DELETE /proxies/{name}/weights` | One group | Counts of removed entries: `{"group", "deleted": {"aggregate", "site", "exact", "blocks"}}` |
| `POST` / `DELETE /cache/smart/flush/{name}` | One group (all of them when the name is not a Smart group) | 204 |
| `POST` / `DELETE /cache/smart/flush` | Every Smart group of the current config | 204 |

Flushing removes the group's evidence, incumbents, serving pool and exploration budget, every block record (including `manual`), group-wide blocks, the manual pin, exit info and all of its records in the cache file; health state is reset, and a `smart-loadbalance` group returns to its configured lock and settings and re-detects regions. Use it after a big change of nodes, or when you suspect the data was skewed by something unusual.

## Memory

Evidence cells live in tables shared by all Smart groups, each split into 64 shards and evicting approximately the least recently used cell when full:

| Table | Capacity |
|---|---|
| Global and family | 4096 cells |
| Service | 8192 cells |
| Exact target | 16384 cells |

Up to 4096 incumbents are kept; block records are per site and cleaned up after a week without a failure. `cache` in the diagnostic endpoint shows each table's size and total evictions; if evictions keep climbing fast, you visit far more services than fit, and the less used ones restart learning more often.

## Cost per connection

The selection path is built for groups with many nodes:

- The serving pool limits each scoring pass to a few members, and members outside it are only sorted when fallbacks are needed;
- Reading evidence takes no write lock, health is a lock-free snapshot, and connection counters are atomics; scoring is only updated on connect, first response, progress (at most once per second), goodput windows and close;
- Connection quality, LightGBM inference, block judgement and response probes run in the background after a connection closes, never slowing the connection itself.

In parallel benchmarks on an i7-14650HX, for a group of 100 members: engine selection takes about 2.3 µs with 3 allocations; the whole dial plan, filtering, selection and ordering included, about 6.4 µs with 7 allocations.

## Phones and low-memory devices

- The default `interval: 5m` and `idle_timeout: 30m` already save power: health checks pause when the group is unused, and all background tasks skip while the system sleeps;
- Leave `use_lightgbm` and `collect_data` off unless you need them: they open the ASN and country databases, and the model itself takes some memory;
- Leave `prefer_asn` off unless you need ASN grouping, which also spares the ASN database.
