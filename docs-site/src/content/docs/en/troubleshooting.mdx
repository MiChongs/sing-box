This page is organized by symptom. Find the section closest to what you see; each lists likely causes, how to confirm, and how to fix. Terms are in the [Glossary](../glossary/); every endpoint is described in [Clash API](../clash-api/).

## Gather this first

1. **`GET /smart/groups`**: confirms the group type, member count, and switches such as `preferASN` and `useLightGBM`.
2. **`GET /smart/groups/{name}/diag`**: selection reasons, serving pool, block records, failure flood, ASN claims. Most questions are answered here.
3. **`GET /group/{name}/weights`**: each member's reliability, failure streak and pool membership.
4. For per-connection detail, set the log level to `debug`. Smart logs dial failures, convergence, site refusals and blocks with the prefix `outbound/smart[<group>]`, for example:

   ```text
   DEBUG outbound/smart[auto]: dial HK-02 for api.example.com failed: i/o timeout
   DEBUG outbound/smart[auto]: node HK-05 lowWeight for [*.example.com]
   ```

5. The node each connection finally used: `chains` in `GET /connections`.

## Startup fails after upgrading

`json: unknown field "algorithm"` (or `hysteresis`, `use_asn`, `asn_database`, `max_host_failed_times`): these fields were removed in the rewrite. Delete them; replace `use_asn` with `prefer_asn`, and a custom ASN database with `experimental.geox.url.asn`. The mapping is in [Removed fields](../config/#removed-fields).

`policy_priority` fails to parse: the syntax is now `pattern:factor`; the old `=`, `~` and `!` prefixes mean nothing special any more, and factors must be positive.

## Learned data is lost on restart

- The command-line version runs without `experimental.cache_file`, so Smart only learns in memory.
- Data is written every 5 minutes; killing the process loses the last few minutes.
- The group was renamed: data is keyed by group name, so the new name starts from zero.
- Upgrading from the old Smart: the old `smart_stats` data is not migrated and is deleted automatically.

## A node is never chosen

Find the node in `weights` and `diag` and go through this list:

| What you see | Cause |
|---|---|
| `Alive: false`, `alive: false` in `diag` | Two health checks in a row failed. Check that `url` and `expected_status` suit this node |
| `blocked: "unstable"` in `diag` | The stability check saw jitter or a slowdown; blocked group-wide for 12 minutes |
| `blocked: "manual"` in `diag` | Blocked through `POST /smart/groups/{name}/block/{node}`; `DELETE` on the same path lifts it |
| `FailStreak` 3 or more | Consecutive node-level failures; no trials during the backoff (`BackedOff`); see [Failure state](../scoring/#failure-state) |
| A block for some site in `hosts` | Unusable for that site only; see [Block codes](../blocks-and-probes/#block-codes) |
| `Pool: false` with few `Completed` | Not in the serving pool. With many nodes the pool holds only a few, and an outside member rotates in every 10 minutes to be compared; this is normal |
| `Observed` clearly below others | More than 0.05 behind on reliability, so not eligible |

A node with a lower `policy_priority` factor loses to higher-factor nodes when reliability is close; the factor does not rule it out, but it rarely wins.

## It sticks to one node and never switches to a faster one

Usually by design: each service has an incumbent, and a challenger replaces it only by proving a gain on data that is **mature on both sides**. When `incumbentHeld` and `insufficientEvidenceHeld` dominate the reasons in `diag`, this is what is happening.

- The challenger has to gather data on the same service, through exploration and rotation, which can take minutes to tens of minutes;
- Latency is only a small part of the score, so a more reliable node wins even when it is a bit slower;
- To switch right now, pin a node or flush the group.

## Nodes keep switching back and forth

A growing `switchFlap` in `diag` means a few nodes perform almost identically. Give one of them a slightly higher `policy_priority` factor (say 1.05) to break the tie, or put the similar nodes in a `urltest` group and hand that to Smart.

## A working node gets blocked

- **`lowWeight`**: connection quality × factor below 0.4. Nodes with a factor below 1 trigger it more easily; with `use_lightgbm`, the model's predictions may also run low.
- **`error`**: `max_failed_times` errors in a row on one site. If the site itself is flaky, raise the value.
- **`answer`**: the site refused the node (403, a challenge, region unavailable, …); usually a real refusal, see the next section.
- **`manual`**: set by `DELETE /connections/smart/{id}`; permanent until the group is flushed.
- Many nodes blocked at once: when more than a third of the members are blocked, the site itself is judged broken and the blocks are ignored (`hostBlocked: true`); no blocks are made during a failure flood.

## A site keeps saying "not available in your region" or shows challenges

Response probes recognize this and block refused nodes for the site with `answer`; when several exits of one region are refused, the whole region is deferred for that site (an exit suspicion). To confirm:

- `node <node> refused for <site>: <reason>` in the `debug` log;
- `answer` records for the site in `hosts` of `diag`, and `members[].exitRegion`.

If every node is refused, Smart blames the site and pauses blocking for 30 minutes; only another line or subscription helps then. A rule of its own for the site makes all its domains converge on a node that works.

## The pin is released, or the pinned node does not work

- **A group delay test releases the pin** (as in mihomo). Testing a Smart group in the dashboard does that; testing the group as one proxy (`GET /proxies/{name}/delay`) does not.
- The node left the group (renamed or removed by a subscription update), so the pin was released.
- When the pinned node cannot connect, the connection fails; there is no fallback.
- UDP connections are selected automatically when the pinned node has no UDP.

## Connections get dropped

Smart closes connections itself at these moments:

- **Convergence**: after the primary fails and a fallback connects, the service's TCP connections through other nodes are closed (log: `converged N connections of [...]`);
- **A block takes effect**: when a node is blocked for a service, the service's TCP connections are closed;
- **The pin changes** with `interrupt_exist_connections` on;
- A site gets a site key for the first time (`prefer_asn`).

None of these count as success or failure, and clients usually reconnect at once. If one service keeps getting dropped, check its block records in `diag`.

## prefer_asn has no effect

- The ASN database is still downloading: the `debug` log shows `ASN database ... is downloading`; it takes effect once downloaded.
- No destination IP at routing time: with FakeIP, or domains that were never resolved, there is no ASN and Smart works per site. Add a `resolve` action to your rules.
- The destination is on a shared network (Cloudflare, Akamai, AWS, …): per site by design.
- The rule is not broad: specific rules (`geosite-netflix`, `domain_suffix`) always key by the rule; see [prefer_asn](../service-keys/#prefer_asn).
- `asnClaims` is 0 in `diag`: not enough evidence from service rules yet; claims are recomputed every 2 minutes.

## The LightGBM model has no effect

- No `lightgbm model loaded from …` in the log: the model is still downloading, or the download failed (check `download_detour` / `http_client`).
- WARN `lightgbm: cannot use model …`: the file is not a LightGBM text model or is damaged; delete it to download again.
- The model loaded but the CSV still says `Traditional`: its `[transforms]` section has an `[order]` that differs from Smart's feature order, or the node has fewer than 2 completions on that service.
- Your own model was overwritten: with `auto_update` on, the model at `url` replaces the local file.

## Training data stops growing

- The file reached `size_limit_mb` (100 MB by default) and writing stopped; delete it and a new one is created within 5 s.
- Only groups with `collect_data` write; with `sample_rate` below 1 only some connections are recorded; dial failures and inconclusive connections never are.
- Rows are flushed every 100; the newest may still be in the buffer.

## The failure-flood warning appears

`failures are flooding in, learning paused until a connection succeeds` means 50 failures in a row within a short time, usually a network outage. Meanwhile failures count against no node, and learning resumes with the first successful connection. If it appears often while the network is fine, check whether every node is dead (an expired subscription).

## Battery drain or heat on phones

- Keep the default `interval: 5m` and `idle_timeout: 30m`; health checks pause when the group is unused;
- Turn off `use_lightgbm`, `collect_data` and `prefer_asn` unless you need them;
- Avoid several Smart groups over the same large subscription: each one checks and learns separately.

## Smart load balancing

### Config errors

| Error | Cause and fix |
|---|---|
| `unknown balance strategy: ...`, `unknown balance affinity: ...`, `unknown region mode: ...`, `unknown region fallback: ...` | A misspelled value; valid values are in [Configuration](../config/#smart-loadbalance) |
| `region.mode priority requires region.priority` | The `priority` mode needs `region.priority` |
| `region.outbounds.tag must contain {region}, {name}, {name_en} or {flag}` | The tag template of region outbounds has no region placeholder, so generated tags would collide |
| `register region outbound <tag>: ...` | A generated region outbound collides with an existing tag. Change the `region.outbounds.tag` template or the existing outbound's tag |
| `smart-region[<tag>]: <group> is not a smart-loadbalance group` | A hand-written `smart-region` points at a group that is not `smart-loadbalance` |
| `dependency[...] not found` when referencing a region outbound | Only the region outbounds listed in `region.outbounds.regions` exist at startup; outbounds created at runtime by `auto` cannot be referenced in the config |

### A node lands in the wrong region

**Confirm**: `GET /smart/groups/{name}/regions` lists every node's region and `source` (`rule`, `name`, `exit`, `unknown`).

**Fix**: when name detection is wrong, correct it with `region.rules` by regex or node name; to trust the real exit, set `detect.exit: prefer` and call `POST /smart/groups/{name}/regions/detect?force=true` to probe again.

### Error `no available member for ...`

`smart-loadbalance` found no candidate at all:

- Other regions have healthy nodes, but `region.fallback` keeps the connection away from them (`none`, or `priority` with no listed region healthy). Set `fallback` to `auto`, or add more regions to `priority`.
- The confined region (a region outbound without `fallback`, or a region locked with `fallback: none`) has no members at all.

When the allowed scope has no healthy node at all (after a long outage, say), the group does not fail outright: it ignores health and tries members in quality order. A node only counts as unhealthy with a global failure streak of 3 during its backoff, failed health checks, a failed last probe, or a group-wide block.

### Connections always land on the same node

- Is `balance.affinity` `target`, `site` or `source`? Those bind sets of connections to one node;
- Is only one node left in the pool? `min_quality` too high, `max_nodes: 1`, or other nodes of the region unavailable;
- Is a node pinned in the dashboard?

### Exit detection never produces a result

Exit detection requests `detect.exit_url` through the node; it fails when the node is down or the URL is blocked, and retries after 30 minutes. The `debug` log records `exit probe [<node>] failed: ...`. Try another URL that returns a country, such as a JSON API with a `country_code` field.

### No destination country (destination mode)

First make sure the country database has downloaded: GeoX downloads it in the background, and until then only domain suffixes help. With FakeIP, resolving yields fake addresses with no country; rely on `destination.map` and country TLDs, or use the `auto` mode.

## Resetting all Smart data

| Method | Scope |
|---|---|
| `DELETE /proxies/{name}/weights` | One group: everything learned, blocks, the pin, and the region lock and exit results of `smart-loadbalance` |
| `POST /cache/smart/flush` | Every Smart group of the current config |
| Stop sing-box and delete the cache file | Everything, **including** other caches such as rule sets, FakeIP and selector state, and data left by groups removed from the config |
