`smart-loadbalance` is a "load balance by region" group: hand it every node of a subscription, and it sorts them into regions on its own, picks a region for each connection, then spreads connections over several good nodes in that region. It suits large subscriptions where you want traffic spread out while each site keeps the same exit country, and it works well as the front of chained proxies (landing nodes).

How it compares with the other two group types:

| | `loadbalance` | `smart` | `smart-loadbalance` |
|---|---|---|---|
| Node per connection | Round-robin / hash / sticky | The learned best node (fine-tuned among the top few) | Spread over every good node of the chosen region by quality and load |
| Knows good from bad nodes | Only whether probes pass | Learned per destination | Learned per destination |
| Regions | None | None | Sorted automatically, region chosen per destination |
| As the front of chained proxies | Possible, but region-blind and keeps using bad nodes | One front node | Front spread within a region; region lockable or matched to the landing server's country |

Everything `smart` does — learning, circuit breakers, the watchdog, persistence, LightGBM, ASN — works the same here, and every `smart` field except `algorithm` and `hysteresis` keeps its meaning. Terms such as "destination", "weight" and "circuit breaker" are explained in the [Glossary](../glossary/).

## Three-minute setup

### 1. Minimal config

```json
{
  "type": "smart-loadbalance",
  "tag": "balance",
  "providers": ["my-subscription"]
}
```

With nothing else set, the group:

- detects regions from node names, and finds the region of nodes whose names say nothing with an exit probe;
- picks the best region for each site automatically and remembers it for 30 minutes;
- spreads connections inside a region by node quality and current connection count;
- does not bind connections to a fixed node.

As with `smart`, **`experimental.cache_file` must be enabled** for the group to learn; without it, it can only judge nodes by probe latency.

### 2. The three settings people change most

```json
{
  "type": "smart-loadbalance",
  "tag": "balance",
  "providers": ["my-subscription"],
  "balance": { "affinity": "site" },
  "region": {
    "mode": "auto",
    "outbounds": { "enabled": true, "regions": ["HK", "JP", "US"] }
  }
}
```

| Setting | What it does | When to change it |
|---|---|---|
| `balance.affinity: "site"` | Keeps all connections to one site (such as `*.openai.com`) on the same node | Sites with logins that drop or trigger checks when the exit IP changes. Keep the default `none` when you only want faster downloads or use the group as a proxy-chain front |
| `region.outbounds.enabled` | Generates one outbound per region, such as `balance-HK` and `balance-JP` | You want to switch regions in a dashboard, or have landing nodes and route rules use a specific region |
| `region.mode` | Decides which region each connection uses | The default `auto` picks per site; use `destination` to match the destination's country, or `priority` to use a few regions in a fixed order |

With `region.outbounds` on, the `balance` group lists its region outbounds in dashboards; picking one locks the whole group to that region, and "unpin" returns it to automatic choice.

### 3. Check that it works

The startup log shows how many nodes each region has:

```
smart-loadbalance[balance] regions: HK(12) JP(8) SG(5) US(4) OTHER(1); mode=auto strategy=smart affinity=site fallback=auto
```

`OTHER` holds nodes whose region could not be detected. To see which nodes they are and how each node was placed:

```bash
curl http://127.0.0.1:9090/smart/groups/balance/regions
```

With `log.level` set to `debug`, every connection logs the region it chose, how it picked the node, and how many nodes were in the pool:

```
smart[balance] select via auto region=HK pick=smart pool=8: target=*.openai.com asn=[none] candidates=[HK-03,HK-01,HK-02,...]
```

See [Examples](../examples/#smart-load-balancing) for complete configurations and [Configuration](../config/#smart-loadbalance) for every field.

## Worked example: who gets the next connection

Here is the choice with the default settings (`mode: auto`, `strategy: smart`), step by step with real numbers. "Quality" is Smart's score for a node, roughly between 0 and 1.2, higher is better; where it comes from is explained under [Region modes](#region-modes).

**Step 1: choose a region.** A user opens `*.openai.com`; both Hong Kong and Japan have usable nodes:

| Region | Healthy nodes | Best 3 qualities | Mean | Pool-size bonus | Region score |
|---|---|---|---|---|---|
| Hong Kong | 8 | 0.90, 0.85, 0.80 | 0.85 | ×1.15 | 0.98 |
| Japan | 2 | 0.95, 0.90 | 0.925 | ×1.05 | 0.97 |

Hong Kong scores higher, so the site goes to Hong Kong and remembers it for 30 minutes. Japan would have to beat 0.98 × 1.25 ≈ 1.22 to take over, so small fluctuations do not make the site hop back and forth.

**Step 2: pick a node.** Say the Hong Kong pool has 3 nodes. The `smart` strategy gives each node a "cost" of (current connections + 1) ÷ quality; the lower the cost, the more the node deserves the next connection.

| Node | Quality | Connections | Cost |
|---|---|---|---|
| HK-01 | 1.00 | 3 | 4 ÷ 1.00 = 4.00 |
| HK-02 | 0.80 | 2 | 3 ÷ 0.80 = 3.75 |
| HK-03 | 0.60 | 0 | 1 ÷ 0.60 = 1.67 |

The lowest cost is 1.67, and only nodes within 1.1× of it (1.83) take part in the draw, so the next connection goes to HK-03.

After HK-03 has taken two connections, its cost is 3 ÷ 0.60 = 5.00. Now HK-02 is cheapest at 3.75, the limit is 4.13, and HK-01 at 4.00 is within it, so the two share a quality-weighted draw: about 56% for HK-01 (1.00 ÷ 1.80) and 44% for HK-02.

Over time, each node's connection count is proportional to its quality — here roughly 10 : 8 : 6. Better nodes do more of the work, and weaker ones still help.

## Region detection

Each member gets its region from the first of these that applies:

1. **`region.rules`**, in order: a regex on the name, or an explicit list of members.
2. **Exit probe** (with `detect.exit: prefer`): a valid probe result.
3. **Member name** (unless `detect.disable_name` is set): see below.
4. **Exit probe** (the default `fallback`): the result for members the name could not place.
5. **Nothing matched**: handled by `region.unknown`, by default the `OTHER` region.

Provider members lose their `provider/` tag prefix before detection, so a provider named `jp-sub` does not make every member Japanese. Members can be plain nodes or other groups.

### Names

The detector collects every region hint in the name and scores it: country and city names (Chinese or English) score 3, flags 2, ISO / airport codes 1. The highest total wins; on a tie the later hint wins, because relay names put the exit last.

| Member name | Region | Why |
|---|---|---|
| `🇭🇰 香港 01`, `HK01`, `hk-bgp-1` | HK | Flag, Chinese name, code (digits may follow directly) |
| `Japan Tokyo 02`, `JP-NRT-3` | JP | English country and city, airport code |
| `沪日 IPLC 01`, `IEPL 深港 2` | JP, HK | Private-line shorthands |
| `香港中转美国`, `HK → JP` | US, JP | An entry region followed by "中转" / "→" barely counts |
| `美国 洛杉矶 [HK中转]`, `CN2 GIA 洛杉矶` | US | `CN2` is a carrier backbone, not China |
| `🇨🇳 台湾 01` | TW | Mainland China in a name only counts when nothing else matches |
| `印度尼西亚 01`, `白俄罗斯` | ID, BY | Longer names win, so not India or Russia |
| `🇺🇸 US LA 01` | US | `LA` and `NY` in names are US cities |
| `Ｈｏｎｇ Ｋｏｎｇ` | HK | Full-width characters are normalised first |
| `剩余流量：100.5 GB`, `节点 NO.1` | none | Traffic units and numbering are not Britain or Norway |

The name table covers 94 countries and regions with common cities and airport codes; flags work for any country. Two-letter codes that read like words or labels (`NO`, `ID`, `IT`, `CO`, `AT`, …) are ignored; those regions are detected from flags and names.

When detection gets a node wrong, correct it with `region.rules`:

```json
"rules": [
  { "region": "IPLC", "name": "Private line", "match": "(?i)IPLC|IEPL" },
  { "region": "JP", "outbounds": ["mystery-node-7"] },
  { "region": "HK", "name": "HK picks", "icon": "https://example.com/hk.png" }
]
```

`region` can be a built-in or a custom region (like `IPLC` above). A rule with only `region` and `name` / `icon` matches no member; it only renames or decorates the region.

### Exit probes

An exit probe fetches `detect.exit_url` (default `https://www.cloudflare.com/cdn-cgi/trace`) through the member and reads its exit IP and country. That is the address websites actually see, which helps most with members whose names are missing or wrong, or whose entry is a domestic relay.

- `fallback` (default): probes only members that the rules and the name could not place.
- `prefer`: probes every member not placed by a rule, and the result overrides the name. With many members the first round takes a while; names are used meanwhile.
- `off`: no probes.

Probes run after start and after subscription updates, and every hour the group checks for results that have expired; at most `exit_concurrency` (default 4) run at once. Results last 24 hours (`exit_ttl`) and are saved in the cache file, so a restart reuses them; a failed member is retried after 30 minutes. `direct`, `block` and `dns` members are never probed.

`GET /smart/groups/{name}/regions` shows every member's region and its source (`rule`, `name`, `exit`, `unknown`); `POST /smart/groups/{name}/regions/detect?force=true` re-probes every member. See [Clash API](../clash-api/#smart-load-balancing).

## Region modes

`region.mode` picks the primary region of each connection; when the primary region cannot serve, `region.fallback` decides which regions to use instead.

Two scores come up below:

- **Node quality** is, in order: the weight the node has learned for this destination; the node's overall weight across all destinations × 0.9; a value derived from its probe latency (0.4 + 0.4 × 300 ÷ (300 + latency in ms), so 100 ms gives 0.70); or 0.55 when there is nothing else. It is then multiplied by the node's `policy_priority` factor.
- **Region score** is the mean quality of the region's 3 best healthy nodes, times a pool-size bonus (+5% per doubling, at most +20%), the region's factor in `region.weights`, and the region-probe result. Nodes whose learned weight for this destination is below 0.4 count half.

### auto (default)

Picks the best-scoring region for each destination and remembers it for `sticky` (30 minutes by default, refreshed on every use). While it is remembered:

- other regions are compared at most every 30 s, and must score `switch_margin` (25% by default) higher to take over;
- the destination moves at once when its region drops below `min_nodes` healthy nodes;
- after a dial fails over into another region and succeeds, the memory follows the new region.

So a site keeps its exit country unless another region is clearly better or its region goes down.

### destination

Picks the region by the country the destination is in — for games, local streaming, and choosing the front by where the landing server is. The country comes from, in order:

1. the destination IP in the country database;
2. the domain's country-code TLD (`.jp`, `.co.uk`, …; turn off with `destination.disable_tld`). Suffixes commonly used as generic domains, such as `.io`, `.co`, `.tv`, `.me`, `.ai`, are never used;
3. the IP of the domain resolved through the DNS router (turn off with `destination.disable_resolve`). The lookup waits at most 300 ms and is cached per domain for 10 minutes (1 minute on failure), so a landing server configured by name is still matched by where it is. For websites behind a CDN this yields the country of the edge nearest the DNS server; with FakeIP it yields no country.

`destination.map` maps a country to a list of regions, for example `{"KR": ["JP", "HK"]}`: a destination in Korea tries Japan, then Hong Kong. Countries without a mapping look for the region with the same code. When the country is unknown or none of the listed regions is available, `auto` decides.

This mode needs the country database. When the mode is `destination` or `destination.map` is set, GeoX starts downloading it in the background at startup (`experimental.geox.url.mmdb`, or the default GeoLite2-Country); switching to `destination` at runtime starts the download then. Until it arrives, only TLDs can tell the country.

### priority

Takes the first region in `region.priority` that has at least `min_nodes` healthy nodes (or, when none does, the first with any healthy node), so `priority` must be set (startup fails otherwise). When none of the listed regions is available, `fallback: auto` uses the best-scoring other region; with `fallback` set to `priority` or `none`, regions outside the list are not used — see [When nothing is healthy](#when-nothing-is-healthy).

### off

No regions: every node (in regions allowed by `allow` / `deny`) is in one pool. For "load balancing with learning" when the exit country does not matter.

### Locking a region

Pick a region outbound in a dashboard, or set `lock` with `PUT /smart/groups/{name}/regions`, to lock the group to one region; a lock overrides the region mode. It is saved in the cache file and survives restarts. When the locked region cannot serve, `fallback` applies; set `fallback: none` to never leave it.

### Fallback

| `region.fallback` | Primary region unavailable | Dial candidates |
|---|---|---|
| `auto` (default) | The best-scoring other region | Up to 7 nodes of the primary region, then the best nodes of the fallback regions (up to 2 regions, 3 nodes in all) |
| `priority` | The next region in `priority` | Same, with fallback regions limited to `priority` |
| `none` | No other region is used | Primary region only |

`allow` / `deny` restrict which regions can be chosen or fallen back to; `min_nodes` (default 1) is how many healthy nodes a region needs to be chosen — when no region reaches it, the best region with any healthy node is used. A locked region and region outbounds ignore `allow` / `deny` and need just one healthy node.

### When nothing is healthy

Health data — probes, circuit breakers — can be stale or wrong. So when no healthy node can be chosen, the group does not give up at once: like a `smart` group, it dials the members in scope anyway, best quality first, and one success brings it back to normal:

- the chosen region's healthy nodes are all soft-blocked for this destination: it retries within that region;
- a region outbound (without `fallback`), or a region locked with `fallback: none`, has no healthy node: it retries within that region only and never leaves it;
- otherwise, when no allowed region has a healthy node: it retries across all allowed members.

A connection only fails, with `no node can serve ...`, when other regions do have healthy nodes but `region.fallback` keeps the connection away from them (`none`, or `priority` with no listed region healthy). In the debug log, the source of such a last-resort dial ends with `(last resort: no healthy node)`.

## Region probes

The `auto` mode learns from real traffic, but traffic only flows through the region it already picked, so how the other regions do for that destination stays unknown. Region probes fill that gap: every `probe.interval` (10 minutes by default), the group takes the `probe.targets` (6) most visited HTTPS sites and times connecting to each site and completing a TLS handshake through the best node of each of the top `probe.regions` (5) regions.

Results stay valid for 3 intervals and scale the region scores:

- a region with a result is multiplied by "fastest region's time ÷ this region's time", no lower than 0.35;
- a region whose probe failed is multiplied by 0.25;
- a region without a result while other regions have one for the same site is multiplied by 0.85.

Only domains reached over TCP 443 are probed. The first round runs about 90 s after start; rounds are skipped while the group is idle (no dial for 2 minutes), the network is down, a region is locked, or the mode is `priority` or `off`. Probes go through Smart's shared probe queue and its concurrency limit. Set `probe.disabled: true` to turn them off.

## The node pool

Once a region is chosen, the group builds a pool from the region's members:

1. Healthy nodes only: circuit breaker closed, not marked unavailable in the last 3 minutes, last probe not failed, not blocked; UDP connections also need UDP support. An old probe result does not count as a failure: health checks pause while the group is idle (no dial for 2 minutes), so results naturally go stale.
2. Nodes soft-blocked for this destination are dropped; nodes that failed often for it recently have their quality ×0.3.
3. Nodes whose learned weight for this destination is below 0.4 are dropped as long as other nodes remain.
4. Nodes below the best node of the pool × `min_quality` (0.5 by default) are dropped.
5. With `max_nodes`, only the best ones are kept.
6. With `max_connections_per_node`, nodes at the cap are skipped, unless all of them are.

## Strategies

`balance.strategy` picks which node of the pool carries the connection. "Load" in the table is the node's live connections through this group (TCP and UDP) plus dials in flight, so a burst of simultaneous connections spreads too.

| Strategy | Aliases | Behavior |
|---|---|---|
| `smart` (default) | `auto`, `adaptive` | Cost is (load + 1) ÷ quality; nodes within 1.1× of the lowest cost share a quality-weighted draw. Over time connections are proportional to quality; see the worked example above |
| `least-connections` | `lc`, `least-conn`, `least-loaded` | Lowest load; ties are a quality-weighted draw |
| `round-robin` | `rr` | Takes turns in name order, counted per region |
| `weighted-round-robin` | `wrr`, `weighted-rr` | Smooth weighted round-robin (as in nginx): deterministic and interleaved in proportion to quality |
| `weighted-random` | `wr` | Quality-weighted random |
| `random` | | Uniform random |
| `consistent-hashing` | `chash`, `hash`, `rendezvous` | Weighted rendezvous hashing: the same key (the affinity key, or the destination without affinity) keeps landing on the same node; when a node leaves, only its own keys move |

Values are case-insensitive, and `_` and spaces count as `-`. Unlike the `algorithm` of `smart`, a misspelled value **is a config error**.

## Affinity

`balance.affinity` keeps a set of connections on one node, so a site or a device does not hop between exit IPs:

| Value | Bound together | Use for |
|---|---|---|
| `none` (default) | Nothing; every connection is placed on its own | Downloads, the front of chained proxies — anywhere the load should really spread |
| `target` | Same destination, such as `*.example.com` | General browsing |
| `site` | Same registrable domain, such as `img.example.com` and `api.example.com` | Sites that tie logins or risk checks to the exit IP (AI services, banks, some streaming) |
| `source` | Same client IP | Per-device placement on a LAN |
| `source-site` | Same client, same site | Similar to `sticky-sessions` of `loadbalance` |

Bindings are kept per region for `affinity_ttl` (10 minutes by default, refreshed on every use). A binding whose node is no longer in the pool (unhealthy, soft-blocked, at its connection cap) is placed again and updated. `PUT /smart/groups/{name}/balance` switches affinity at runtime; changing it drops the existing bindings.

<Callout type="note" title="Affinity versus spreading">
  The wider the affinity, the more connections share one node. Do not set `target` or `site` on the front group of chained proxies: every connection to the same landing server would land on one front node, which defeats the spreading.
</Callout>

## Dialing and failover

Unlike `smart`, round 0 dials only the picked node, without racing the runner-up, so the distribution holds. When the picked node looks suspect (recent dial failures, marked unavailable, or no successful dial or probe yet), the next node of the pool is hedged after 250 ms and whichever connects first wins. Then up to 3 more rounds dial 3 candidates each: first the rest of the pool, then the fallback regions. The candidate list holds at most 10 nodes, exactly what these 4 rounds reach. If everything fails, the group selects once more with the updated circuit-breaker state.

## Region outbounds

With `region.outbounds.enabled`, the group generates `smart-region` outbounds for regions:

```json
"region": {
  "outbounds": {
    "enabled": true,
    "regions": ["HK", "JP", "US"],
    "tag": "{flag} {name_en} LB"
  }
}
```

This creates `🇭🇰 Hong Kong LB`, `🇯🇵 Japan LB` and `🇺🇸 United States LB` (the default template `{group}-{region}` gives tags like `balance-HK`). Connections through a region outbound still run the group's full pipeline — learning, circuit breakers and spreading are shared with the group — with the region fixed.

- Outbounds listed in **`regions`** are created at startup and can be referenced by route rules, `detour` and `selector`.
- **`auto`** (implied when `regions` is empty) creates outbounds for regions that appear at runtime and removes them when the region disappears. Outbounds created at runtime cannot be referenced from the configuration.
- **`members`**: by default `regions` — the group lists its region outbounds as members in dashboards, and picking one locks that region; with `nodes` it keeps listing nodes.
- **`fallback`**: whether a region outbound may use other regions when its own has no usable node. Off by default: it then only retries within its own region (see [When nothing is healthy](#when-nothing-is-healthy)) and never switches to another one.
- Each region outbound can pin one of its own region's nodes in a dashboard without affecting the group.

Region outbounds can also be declared by hand, for example to set `fallback` or `hidden` for one region:

```json
{ "type": "smart-region", "tag": "japan-front", "group": "balance", "region": "JP", "fallback": true }
```

## Chained proxies (front + landing)

A landing node (your own VPS, a static residential IP and so on) can connect through provider nodes with `detour`: outsiders only see the provider node, and the route may be better. The hop through the provider node is called the front. With a `smart-loadbalance` group or one of its region outbounds as the `detour`, front traffic spreads over several provider nodes and stays in a suitable region:

```json
{
  "outbounds": [
    {
      "type": "smart-loadbalance",
      "tag": "front",
      "providers": ["my-subscription"],
      "region": {
        "mode": "destination",
        "outbounds": { "enabled": true, "regions": ["HK", "JP"], "members": "nodes" }
      }
    },
    { "type": "shadowsocks", "tag": "landing-us", "server": "us.landing.example.com", "server_port": 8388,
      "method": "aes-256-gcm", "password": "landing-password", "detour": "front" },
    { "type": "shadowsocks", "tag": "landing-hk", "server": "hk.landing.example.com", "server_port": 8388,
      "method": "aes-256-gcm", "password": "landing-password", "detour": "front-HK" }
  ]
}
```

- `landing-us` uses the group itself as its front. The group sees the **landing server** as the destination, not the website you open: the `destination` mode picks the front region by the landing server's country (resolving its domain first), and `auto` learns the best front region for each landing server.
- `landing-hk` always uses the Hong Kong front (`front-HK`, generated by `region.outbounds`).
- The front group keeps the default `affinity: none`, so connections to one landing server spread over several nodes of the region, and one throttled or blocked provider node does not take them all down.
- The landing nodes may themselves sit in a `smart` or `selector` group: the front group recognises the dial as one hop of a proxy chain and learns and picks regions for the landing server rather than for the outer website.

## Runtime control

| Action | How |
|---|---|
| See regions, members, detection sources, load and quality | `GET /smart/groups/{name}/regions` |
| Lock / unlock a region, switch the region mode | `PUT /smart/groups/{name}/regions`, `DELETE /smart/groups/{name}/regions/lock` |
| Switch strategy and affinity | `PUT /smart/groups/{name}/balance` |
| Re-detect regions, re-probe exits | `POST /smart/groups/{name}/regions/detect` |
| Pick a region outbound or a node in a dashboard | `PUT /proxies/{name}`: a region locks, a node pins |

The lock and any mode, strategy or affinity switched at runtime are saved in the cache file and restored after a restart; `default` or an empty value restores the configured value. See [Clash API](../clash-api/#smart-load-balancing). Pinning a node works as in `smart`; see [Priority and pinning](../priority-and-pinning/).

## Choosing settings

First pick a region mode by purpose:

| Purpose | `region.mode` |
|---|---|
| Not sure; let it decide | `auto` (default) |
| Games, local streaming, or choosing the front by the landing server's country | `destination`, with `destination.map` for substitute regions if needed |
| Only a few regions, in a fixed fallback order | `priority`, with `priority` or `allow` |
| The exit country does not matter | `off` |

Then a strategy and affinity:

| Situation | Suggestion |
|---|---|
| Most cases | `strategy: smart`, `affinity: none` |
| A site must keep its exit IP | `affinity: site` |
| Multi-threaded downloads, more total bandwidth | `strategy: smart` or `least-connections`, `affinity: none` |
| Every node should get the same number of connections | `round-robin` |
| Fixed node per destination, least disruption when nodes come and go | `consistent-hashing` |
| Front of chained proxies | `mode: destination` or `auto`, region outbounds as `detour`, `affinity: none` |
| Provider limits concurrent connections per node | `max_connections_per_node` |

If you only want traffic concentrated on the best node, a `smart` group is all you need. When something goes wrong, see [Troubleshooting](../troubleshooting/).
