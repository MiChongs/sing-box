`algorithm` decides which candidate Smart dials first from the already sorted candidate list. Every algorithm does only one thing: **move one candidate to the first position**. It does not add or remove candidates, and it does not change the weights themselves. For how the candidate list is produced, see [How it works](../how-it-works/#candidate-tiers).

## Overview

| Algorithm | Aliases | Type | How the first position is chosen |
|---|---|---|---|
| `strict-best` (default) | `auto`, `best`, `strict` | Sort-based | No change. The top-ranked node is used directly |
| `weighted-random` | `random`, `weighted` | Pick-based | Random among the top 5, weighted by rank |
| `least-loaded` | `least-load`, `load` | Sort-based | Fewest active TCP connections among the top 3 |
| `fastest-recent` | `fastest`, `recent` | Sort-based | Lowest recent RTT among the top 5 |
| `sticky-session` | `sticky`, `session` | Pick-based | The node last used successfully for this destination |
| `round-robin` | `rr` | Pick-based | In turn, by a group-wide counter |
| `weighted-rr` | `wrr`, `weighted-round-robin` | Pick-based | The top 5 in turn, in a 5:4:3:2:1 ratio of turns |
| `p2c` | `power-of-two`, `two-choices` | Pick-based | 2 random picks from the top 5, the faster one wins |
| `latency-banded` | `banded`, `latency-bands` | Sort-based | The top 5 are grouped into latency bands, random within the lowest band |
| `consistent-hashing` | `consistent-hash`, `chash`, `ch`, `consistent`, `jump-hash` | Pick-based | Hashes the destination to a fixed position |

Values are case-insensitive, and underscores and spaces count as hyphens, so `Least_Loaded` is also valid. An unrecognized value does not cause an error. It falls back to `strict-best` and logs a WARN that lists all valid values. `algorithm=` in the startup log is the algorithm actually in effect.

### Sort-based and pick-based

The two types differ in more than how the first position is chosen:

- **Round 0 dial width**: sort-based algorithms dial the first 2 candidates at once (only 1 when the first-choice node's recent success rate is ≥ 95%). Pick-based algorithms dial only 1.
- **Scenario reordering**: applies only to sort-based algorithms. The first 5 are reordered by peak download speed for downloads and streaming, and by recent RTT for interactive, realtime and voice traffic.

So pick-based algorithms make a more "deterministic" choice, while sort-based algorithms switch to the second node faster when the first choice is slow.

## Algorithm details

### strict-best

Makes no adjustment and dials in weight ranking order. It suits most cases and is the default. Combine it with `hysteresis` to reduce switching back and forth between similar nodes.

### weighted-random

Picks one of the top 5 at random, with probabilities assigned by **rank**, not by weight: 5/15 for 1st place, 4/15 for 2nd, down to 1/15 for 5th. It suits cases where you want to spread traffic over a few good nodes, but not too evenly.

### least-loaded

Picks the node with the fewest active TCP connections among the top 3. On a tie, the higher-ranked node is kept. UDP connections do not count toward load. It suits downloads and many concurrent connections.

### fastest-recent

Picks the node with the lowest recent RTT among the top 5. Recent RTT is a moving average of first-byte latency over roughly the last 30 samples, cached for 250 ms. Nodes without data are left out of the comparison. It suits latency-sensitive traffic when node quality changes quickly.

### sticky-session

Prefers the node last used successfully for the same destination (TCP and UDP are recorded separately). As long as that node is still available, is not judged suspicious, and no node is pinned, Smart takes the fast path and dials it directly, skipping the whole candidate process. When the records exceed 8192 entries, all of them are cleared.

It suits sites that bind the login session to the IP, such as AI services, banks and some streaming services.

### round-robin

Each dial increments the group counter by 1, and the counter modulo the number of candidates picks the first position. The counter is shared by the whole group and does not distinguish destinations. It suits cases where traffic must be spread evenly.

### weighted-rr

Round robin weighted by rank: among the first K candidates (K is at most 5), 1st place appears 5 times in a row, 2nd place 4 times, and so on. It favors good nodes more than `round-robin` does, and spreads traffic more than `strict-best` does.

### p2c

"Power of two choices": picks two different nodes at random from the top 5. If the recent RTTs of both are known and differ, the lower one wins. Otherwise the one with fewer active connections wins. If they are still tied, the first one drawn wins. It balances load and latency, and suits a general-purpose default.

### latency-banded

Splits the top 5 into three bands by recent RTT: below 50 ms, below 150 ms, and 150 ms or above or unknown. It picks uniformly at random within the lowest non-empty band. This avoids always crowding onto the single fastest node, without using nodes that are clearly slower. It suits interactive traffic.

### consistent-hashing

Hashes `t|destination` or `u|destination` with xxhash, then maps the hash to a position in the candidate list with jump hash. While the candidate list does not change, the same destination always lands on the same node. It suits destinations that need a fixed egress IP.

<Callout type="note" title="What consistency depends on">
  The mapping is based on the length and order of the candidate list. When node failures or weight changes alter the candidate list, the destination may map to a different node. For stronger stickiness, use `sticky-session`.
</Callout>

## Switching at runtime

You can switch the algorithm through the Clash API without restarting:

```bash
curl -X PUT http://127.0.0.1:9090/smart/groups/auto/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"algorithm":"p2c"}'
```

```json
{ "group": "auto", "requested": "p2c", "applied": "p2c", "previous": "strict-best" }
```

The request body must be a JSON object. `applied` is the algorithm actually in effect: if you pass an unrecognized value, it is `strict-best`. The switch lasts only for the current run. After a restart, the value from the configuration file is used again.

## Interaction with other mechanisms

- **`policy_priority`** applies before the algorithm: nodes with a factor above 1 are moved to the front first, and the algorithm then picks from the top few.
- **`hysteresis`** applies after the algorithm: as long as the node last used for this destination within the window is still among the candidates, it is moved back to the first position, overriding the algorithm's choice. Unlike `sticky-session`, it does not take a fast path and still goes through the full filtering process.
- **While a node is pinned**, the candidate list contains only the pinned node, and the algorithm has no effect.

## Choosing an algorithm

| Scenario | Recommendation |
|---|---|
| General use, not sure what to pick | `strict-best`, or `p2c` |
| Login session bound to the egress IP | `sticky-session` |
| The same site needs a fixed egress, but occasional changes are acceptable | `consistent-hashing` |
| SSH, remote desktop, interactive web pages | `latency-banded` or `fastest-recent`, plus `hysteresis` |
| Downloads, updates, many concurrent connections | `least-loaded` |
| Spread traffic evenly, avoid overloading a single node | `weighted-rr` or `round-robin` |

Route rules can send different kinds of traffic to Smart groups that use different algorithms. See [Examples](../examples/#groups-per-traffic-type).

<Callout type="note" title="Spreading connections over a whole region">
  These algorithms only reorder the top 3–5 candidates, and `round-robin` and the like ignore regions. To spread connections over every good node of a region while a site keeps its exit country, use [Smart load balancing](../smart-loadbalance/) (a `smart-loadbalance` group).
</Callout>
